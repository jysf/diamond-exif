## [Unreleased]

### Added

- The Exif block builder (SPEC-025, DEC-014 amendment and DEC-015 clarification of 2026-11-27): `exif_core::write::exif_block(source, &BlockOptions)` plans, for a TIFF-structured source, a relocatable block holding the Exif IFD, its Interop IFD and the GPS IFD in the source's byte order. The plan reports the block's length (independent of where it will sit), the Exif and GPS IFD positions and every entry it leaves out, with a typed reason (a MakerNote, an entry that carries an offset, an unsizable field type); `ExifBlock::write(base)` and `write_into` return exactly those bytes for an even base with final offsets, after reading them back through the crate's own walk. A source it cannot rebuild safely, or a budget it would exceed, is a typed refusal with no bytes. A non-empty block refuses a base below 8 (the TIFF header). Checked against ExifTool 13.55 live (the placed block reads as the source, less omissions; a sweep of every tag id ExifTool lists finds the offset-carrying set inside the omitted one) and by the twelfth fuzz target, `exif_block`. Library only; the CLI does not use it, and there is no cross-byte-order request yet (SPEC-041).

### Changed

- Copyright is now its own category, `rights` (SPEC-033, DEC-008 amendment of 2026-11-21): the Exif Copyright tag (0x8298) and a PNG `Copyright` text chunk moved from `authorship` to `rights`. Severity is unchanged (medium), so no `--fail-on` result changes. For a 0.1.0-alpha.1 user, the finding's category is `rights` in text, JSON and CSV, and the JSON summary's `by_category` gains a `rights` key (last). For a JPEG or TIFF, the `all-pii` preview now shows the Copyright finding as kept (it was removed); a PNG preview already showed every finding as kept, because PNG is not strippable in the CLI yet (SPEC-039). The library's `AllPii` strip keeps Copyright in every container (the Exif tag in JPEG, TIFF, PNG and WebP, and a PNG `Copyright` text chunk) while still deleting Artist and Author. `All` and `Everything` still remove it, and still remove every Exif segment whole. Still not covered: XMP `dc:rights` and the IPTC copyright notice, which follow their packets. `Category::Rights` is a new variant of a `#[non_exhaustive]` enum, and `StripSpec` is now full (16 categories in its `u16`).
- PNG and WebP are now strippable in the audit and the CLI's policy preview (SPEC-039, DEC-020 amendment of 2026-11-24, DEC-023). Before, a PNG or WebP preview kept every finding and said the file had not been checked against ExifTool. Now the preview shows `removed` and `kept_unread` dispositions as it does for JPEG and TIFF, JSON has `"strippable":true`, and CSV dispositions are no longer `not_strippable`. The CLI still never writes a file. The library's PNG and WebP strip is checked against ExifTool 13.55 by 239 replayable records, a two-way category judge, and a differential against ExifTool's own writer (`-all=`, `-gps:all=`) in which every difference is classed and pinned. The PNG text keywords `Make` and `Model` are now `camera_model` findings and `TimeStamp` a `timestamps` finding (they were `free_text`). A strip may still refuse, with a typed reason, a file whose preview shows removals; the preview is then not `reliable`. `StripError` messages are container-neutral: `not a JPEG, TIFF, PNG or WebP`, and `the file cannot be cut safely (...)`.

### Fixed

- A JFIF APP0 thumbnail is now reported and stripped (SPEC-040, DEC-012 and DEC-013 amendments of 2026-11-24; found by an external code review). Before, a JPEG whose `JFIF\0` APP0 segment carried the optional uncompressed thumbnail audited `ok` with zero findings, and `strip(Everything)` returned it unchanged while ExifTool extracted the thumbnail. Now the audit reports a `thumbnail` finding (Medium, no range) on a new region kind, `jfif_thumbnail` in text, JSON and CSV (`schema_version` stays 2), and `AllPii`, `All` and `Everything` remove the whole APP0 segment, as `exiftool -all=` does; `Gps` and `GpsAndDevice` keep it and say so. A thumbnail shorter than its header declares is the bytes present plus a `RegionTooShort` issue, so that file's status is `issues`. A JFIF segment without a thumbnail (nearly every real file) is unchanged and never removed. `RegionKind::JfifThumbnail` and `RemovalKind::Jfif` are new variants of `#[non_exhaustive]` enums.
- Strip writer hardening (PATCH-001; found by an external code review). (1) A TIFF or Exif block whose strip/tile/free offset entries share one out-of-line array no longer makes the writer expand it once per entry: a 1,000-entry, 10,000-value case took about 1 GB of memory and now is refused as `Uneditable { PayloadUnreadable }` in 2.7 MB (values expanded per walk are capped at half the blob length, which no real file reaches). (2) A JPEG whose Multi-Picture index lists more than 16 images (more than the audit reads) is now refused with the new `UnstrippableReason::TooManyMpfImages` whenever the strip would remove bytes; before, the strip returned `Ok` with the index entries past the 16th left pointing at the old offsets, and `EmbeddedImage` could leave those images in the file. A strip that removes nothing, or only edits Exif in place, is unchanged. (3) Deleting many entries from one IFD is now linear: 65,535 targeted entries went from 2.22 s to 0.021 s, with byte-identical output.

## [0.1.0-alpha.1] - 2026-11-20

First public pre-release: the `exif-audit` binary. It is a read-only privacy scan for image metadata: point it at files or folders of JPEG, TIFF or DNG and it reports GPS, device serial numbers, authorship, free text, thumbnails, MakerNotes, XMP, IPTC and ICC, with exit codes a CI job can act on. Alpha: the CLI contract (DEC-011) is intended but not frozen.

- Reports in text, JSON and CSV; `--policy` previews what stripping would leave; `--fail-on` turns findings into a failing build (exit 1 findings, 2 usage, 3 incomplete).
- Read-only: it never writes or changes a file, reads nothing but the paths you name, and keeps no state. The strip writer exists in the library only; the CLI does not use it.
- Checked against ExifTool as an oracle, fuzzed (seven fuzz targets in CI) and panic-free by construction.
- Binaries for Linux x86_64 (static), macOS Apple silicon and macOS Intel, with a `SHA256SUMS` file. Unsigned: see the README for the macOS quarantine step.
- `exif-audit --version` also shows the short commit of a release build, for example `exif-audit 0.1.0-alpha.1 (abc1234)`.
- The library crate (`exif-core`) is not published (`publish = false` in `Cargo.toml`); its API is not stable yet.

### Added

- Inventory parity against ExifTool (SPEC-013, test-only; `src/` unchanged): the audit's inventory (every IFD entry as `(group, tag id)`, every located region) is compared with `exiftool -a -u -G1 -H -s` over 247 inputs (178 distinct): hand-built fixtures, the DEC-008 one-entry TIFFs and the three fuzz-seed directories, live and replay (`tests/inventory_oracle.rs`, records in `tests/oracle-fixtures/exiftool-inventory/`). 146 of the 177 comparable distinct inputs agree exactly; 31 differences are pinned as exact multiset differences with a question each, and anything ExifTool lists that the audit does not leaves the file not clean (asserted). Red-proofs: perturbed inventories and records, byte mutations, and six library faults on a mutated copy. Also closes the SPEC-012 and SPEC-017 verify test gaps (`exif_issues` summed over blocks, region `after_scan`, thumbnail pointer types, and three entry-budget cases) and makes two quadratic fuzz-harness guards linear.
- Total entry budget for the tolerant walk (SPEC-017, DEC-001): `exif_core::tiff::entry_budget(len)` (`len / 12`), `Container::entry_count()` and `Error::TooManyEntries { limit }`. The IFD whose declared count would push the retained entries past the budget is omitted whole, one `TooManyEntries` issue is recorded and the walk ends (like `TooManyIfds`). A real file never reaches it (every entry occupies its own 12 bytes); overlapping tables did: a 789,516-byte TIFF naming 511 overlapping SubIFDs parsed to 33,488,386 entries (about 804 MB) and now to 65,536 (1.5 MB). New `tiff_ifd`/`audit` fuzz invariants (`fuzz/shared/entry_budget_invariants.rs`) and three `tiff_ifd` seeds (32 in all). No dependencies.

JPEG-layer and per-Exif-block issues stay separate and are viewed together through `AnyIssue`; `is_clean` needs every layer clean. `Error` gains `ExtraExif`, `RegionTooShort`, `IccChunkMismatch`. The `jpeg_segments` fuzz target now also asserts the `read` invariants (shared with `tests/fuzz_layout.rs`, the extraction re-derived independently and compared both ways) and has 13 new seeds (34 in all). No dependencies.
- JPEG segment walker (SPEC-009, DEC-006): `exif_core::jpeg::{Jpeg, Segment, SegmentKind, JpegIssue}` with `parse`, `parse_strict`, `segments`, `issues`, `is_clean`, `scan_region`, `eoi_offset`, `trailer`, `MAX_JPEG_SEGMENTS` (4096) and `MAX_JPEG_ISSUES` (1024). Payloads, scan region and trailer are borrowed from the input; APPn kinds (JFIF, Exif, XMP, extended XMP, ICC, IPTC, JUMBF) are identified by signature, nothing is decoded. `Error` gains `NotJpeg`, `StrayBytes`, `BadSegmentLength`, `MissingSos`, `MissingEoi`, `TooManySegments`, `TooManyIssues`. ### Changed

- JPEG walker (SPEC-010): a segment length below 2 now skips the marker and both length bytes (four bytes), so one fault is one `BadSegmentLength` issue instead of that plus a `StrayBytes` for the length bytes (DEC-006 reworded). The module docs state that a fill run reaching the end of the input reports `Truncated` at the last `FF` (behaviour unchanged).

- The walk now follows the Exif (0x8769), GPS (0x8825) and, from inside the Exif IFD, Interop (0xA005) pointers as well as `SubIFDs` (SPEC-004, DEC-005); a corrupt GPS IFD is one reported issue and leaves IFD0 and the Exif IFD readable. The next-word of Exif/GPS/Interop IFDs is recorded but not followed. A `SubIFDs` entry declaring more than 512 offsets is now rejected (`TagTooLarge`) before any offset is decoded, so the issue count is bounded by `MAX_ISSUES`.
- `Container::parse` is now tolerant (SPEC-003, DEC-001): only a bad header or an unreadable IFD0 is `Err`; any other bad IFD (IFD1 and later, `SubIFDs`) is omitted and reported as a `ParseIssue`, so one corrupt sub-IFD no longer discards a readable IFD0. `Container::parse_strict` keeps the old all-or-nothing behaviour. Exact-boundary tests added for the depth and IFD-count limits.
