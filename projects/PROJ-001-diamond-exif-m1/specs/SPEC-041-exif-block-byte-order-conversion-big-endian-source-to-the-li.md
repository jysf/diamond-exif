# SPEC-041: Exif block byte-order conversion: big-endian source to the little-endian block, UNDEFINED rule

> **OUTLINE — `cycle: frame`.** This spec exists so its ID is stable and
> siblings can declare `depends_on: [SPEC-041]`. Capture **scope** (Context /
> Goal / Non-Goals) and **dependencies** only — the *approach* is designed
> just-in-time when this moves to `design`. Do not pre-design it here.

## Context

Second spec of STAGE-007 (PROJ-001), split out of SPEC-025 at the 2026-11-27 re-frame: SPEC-025 was framed L, and the seam between building the block and converting its byte order is the cleanest cut. SPEC-025 builds the block in the source's own byte order. This spec adds conversion into the other order. The consumer needs it: its block is always little-endian at irradiance's fixed base (DEC-015, irradiance/DEC-072), and "a big-endian source is converted value by value" (monorail-000's `docs/upstream/diamond-exif-requests.md`, request 1).

Open for design: the answer to question `exif-block-byte-order-sensitive-undefined` (DEC-014 item 3): for each UNDEFINED entry whose contents depend on byte order (candidates 0x8828 OECF, 0xA20C SpatialFrequencyResponse, 0xA302 CFAPattern, 0xA40B DeviceSettingDescription), convert by a rule proved against ExifTool, or leave out and report. Copying one unchanged into the other order is ruled out. Measure the candidate list against the Exif specification and ExifTool first, and measure which source orders real DNG sources carry. Also open: whether little-endian to big-endian is offered too or refused as unneeded.

Cross-repo references are context only and never `depends_on` entries.

## Goal

Given a source in either byte order and a target byte order, the builder returns a block in the target order whose values read the same as the source's (through this crate's reader and through ExifTool), with byte-order-sensitive entries converted by a measured rule or left out and reported. The readback self-check and the `exif_block` fuzz target cover the cross-order path.
